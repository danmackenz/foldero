# Contributing

Thanks for considering a contribution to Foldero. This is a Cowork / Claude Code plugin that governs real user data, so contributions carry a higher-than-usual care requirement.

## Ground rules

Before proposing any change, please read:

1. `references/SUITE-CONVENTIONS.md` — the shared rule-set every skill honours. **Never weaken any guarantee** (never-delete, ≥90% confidence + §2a exception, three-tier sensitivity, atomic units, run-lock, INDEX three-section structure). PRs that relax these will be declined.
2. `ORCHESTRATOR.md` — the orchestration-layer contract.
3. `README.md` — architecture overview and design principles.

## What contributions are welcome

- **Bug fixes in skill bodies** — logic errors, edge cases not handled, cross-reference drift.
- **Reference-doc improvements** — clarifications, better worked examples, additional cross-skill application notes.
- **New atomic-unit signatures** — `Atomic-Unit-Signatures.md` is a growing list of package formats and self-contained-folder patterns.
- **New skill proposals** — via issue first; a new skill should fit one of the existing categorisation buckets (router / chain-linked / standalone mutating / standalone read-only) and not overlap with an existing skill.
- **OS-compatibility work** — Windows and Linux behaviour is currently untested. Issues and PRs adding compatibility notes or adjustments are welcome.

## What contributions are NOT welcome

- **Anything that weakens a SUITE-CONVENTIONS guarantee.**
- **New MCP server dependencies or filesystem watchers.** The plugin is intentionally "no MCP, no watchers, no external network deps."
- **Hardcoded personal / brand data** in shipped files. All user-specific data lives in files carrying the `USER-CONFIGURED` marker, generated by `/organisation-setup`.
- **Changes to `/organisation-setup`'s output-file format without an upgrade path.** Users with existing configs need a migration story.

## Description-length discipline (§0.5)

New or modified skills keep their `SKILL.md` frontmatter `description:` field under 200 characters where possible, never exceeding 250. The plugin lives on shared skill-listing budgets across every account it's installed on — long descriptions cost every user, not just the author. If a description absolutely needs to be longer for routing clarity, note the exception in the PR.

## Testing

Every mutating skill's `## Tested against` section should record at least one live test on a real (or fixture) folder. Include the outcome — what worked, what surfaced findings, what didn't. Read-only skills should record at least one dry-run against a fixture.

The `/folder-lint` skill validates the plugin's own conventions across all skills. Run it against a fixture folder before opening a PR.

## Issue templates

- **Bug report:** include the skill name, the version, the reproducing steps, and the actual vs expected outcome. Anonymise any real content in your description.
- **Feature request:** open with a "why now" — what real-world need does this address that the current 21 skills don't?
- **Reference-doc improvement:** cite the specific rule / worked example that needs improvement and propose the replacement text.

## Code of Conduct

Be kind. Sensitive-content handling is one of this plugin's core value propositions — contributions and discussions should reflect the same care.
